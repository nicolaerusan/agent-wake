agent-wake.

Wake agents from events. A vendor-neutral hub + subscription + thin-ping standard — agents sleep for free and cold-start with zero lost state.

GitHub → The essay →

The problem

Agents today either poll (burn tokens asking “anything new?”) or hold always-on processes waiting for webhooks (fragile, needs a public URL, loses events on crash). agent-wake unifies push and pull: events live in a durable log, agents hold cursors, and a wake is just a hint that something is waiting. Push becomes a latency optimization over pull — so delivery needs no exactly-once machinery.

Three primitives

HubAn append-only log of typed events with stable IDs, plus subscriptions. One tiny process (or a service). The log is the truth.
SubscriptionA filter + a cursor + wake economics (min intervals, coalescing). The cursor is the agent’s entire memory of “where was I?”.
Thin ping{hub, subscription, cursor, pending} — never a payload. The woken agent reads events after its cursor from the hub and acks. Duplicate or stale pings are harmless by construction.

Quickstart

# install (Node ≥ 20, zero dependencies)
npm install -g github:nicolaerusan/agent-wake

# terminal 1 — the hub: durable event log + mailbox
agent-wake hub

# terminal 2 — wake an agent CLI on every event
agent-wake watch --claude    # Claude Code
agent-wake watch --codex     # ...or Codex
agent-wake watch --cmd 'node my-agent.mjs'   # ...or anything

# terminal 3 — play the world: emit an event
agent-wake emit task.created --data '{"title":"hello"}'

The watcher long-polls the hub’s mailbox over an outbound connection (NAT-proof, no public URL), and on each ping shells out to the agent with the ping in $WAKE_PING. The agent cold-starts, reads its pending events, handles them, acks its cursor, and exits. Filter with --types a,b; pass extra flags to the agent CLI after --.

Claude Code & Codex

# headless claude needs permission to curl the hub
agent-wake watch --claude -- --allowedTools 'Bash(curl:*)'

# codex needs network enabled in its sandbox
agent-wake watch --codex -- --sandbox workspace-write \
  -c 'sandbox_workspace_write.network_access=true'

BB

Using bb? The plugin wakes BB threads instead of CLI processes — one thread per ping, with your standing instructions in the prompt:

bb plugin install https://github.com/nicolaerusan/agent-wake --plugin agent-wake
bb wake emit task.created '{"title":"hello"}'

Why thin pings?

  • Polling is always a valid fallback — push is just lower latency, so nothing breaks when a webhook is missed.
  • Exactly-once processing without exactly-once delivery — the cursor at the hub is the truth, not the ping.
  • Agents can be processes, containers, or nothing at all — the wake target is a spawner; a cold agent reconstructs everything from hub + subscription + cursor.
  • Wake economics live in the subscription — min intervals and coalescing keep a chatty event source from becoming a token firehose.

Security, honestly

The reference hub is unauthenticated localhost plumbing — don’t bind it to the internet. Two risks are unique to waking agents: event data is prompt-injection surface (an LLM with tools reads attacker-authored text, so subscribe only to sources you trust and scope the woken agent’s permissions tightly), and the woken agent must never trust the ping’s hub URL — it reads from its configured hub, so a forged ping can at worst make it poll its own log. Subscription ownership (create-time secrets, per-source emit credentials, signed pings for push) is the first post-MVP milestone. The full threat model and hardening roadmap live in SECURITY.md; the essay covers the why.

Prior art it steals from: CloudEvents (envelope) · Standard Webhooks (signing) · WebSub (subscribe/deliver) · ActivityPub (inbox as identity) · SMTP/MX (standardize addressability, not hosting).
